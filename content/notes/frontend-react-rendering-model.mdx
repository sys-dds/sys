## Interview question

A React page feels slow after a user changes filters. How do you reason about what is re-rendering and what to optimize?

## Weak answer

I would add `memo`, `useMemo`, and `useCallback` to stop unnecessary renders. React re-renders too much sometimes, so memoization usually helps.

## Senior answer

Preview: I would first separate render work from commit work, then identify which state change starts the expensive path. A render is React calculating the next UI; a commit is React applying it. Not every render is harmful, and memoization is only useful when it removes meaningful repeated work.

The full note will expand this into profiling steps, state placement trade-offs, list performance, derived data, and when memoization creates more confusion than value.

## Why this sounds senior

It treats performance as diagnosis, not ritual. The answer names what must be measured before choosing an optimization.

## Practical example

Preview: In a filtered activity feed, the bottleneck might be recomputing grouped rows, rendering too many visible items, or pushing filter draft state too high in the tree.

## Checklist

- Identify the state update that starts the work.
- Distinguish render cost, commit cost, data cost, and layout cost.
- Avoid memoizing before measuring.

## Practice task

Pick one slow interaction and write three possible causes before touching the code.

## Final mental model

Rendering is work, but work is not automatically waste. Senior React performance starts by finding the cause.

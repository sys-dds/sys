## Interview question

How do you answer an open-ended frontend architecture prompt without rambling or jumping straight to tools?

## Weak answer

I would say what stack I prefer, describe the components I would build, and mention performance, accessibility, and testing if there is time.

## Senior answer

Preview: I would use a repeatable answer shape: clarify the product goal, identify core user flows, define data boundaries, choose rendering and state strategies, discuss failure modes, then explain trade-offs.

The full note will expand this into reusable answer patterns for frontend system design prompts, including how to move from requirements to architecture without sounding scripted.

## Why this sounds senior

It shows that architecture is a sequence of decisions under constraints. The answer gives the interviewer clear places to go deeper.

## Practical example

Preview: For a billing portal, clarify permissions, invoices, plan changes, payment failure states, and audit needs before choosing component or data-fetching patterns.

## Checklist

- Clarify the product goal and constraints.
- Name the highest-risk user flows.
- Explain trade-offs before naming tools.

## Practice task

Answer this prompt in five minutes: "Design the frontend for a billing portal." Avoid naming libraries until the second half.

## Final mental model

Senior answers are not longer answers. They are ordered answers that make uncertainty visible and decisions traceable.

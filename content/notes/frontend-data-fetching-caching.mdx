## Interview question

Design data fetching for a project management app with dashboards, issue lists, and inline updates. How would you cache data?

## Weak answer

I would use React Query and cache the API responses. After mutations I would invalidate the queries so the UI updates.

## Senior answer

Preview: I would start by classifying data by freshness requirements. Dashboard summaries can often tolerate short staleness. Issue details, permissions, and destructive actions need stricter freshness. Optimistic updates are useful only when rollback is clear and safe.

The full note will expand this into cache layers, invalidation events, server/client ownership, loading states, stale states, and failure behavior.

## Why this sounds senior

It frames caching as a product and consistency trade-off, not only a library decision.

## Practical example

Preview: A dashboard count can revalidate occasionally, while an issue title edit may update optimistically and then refetch related list data.

## Checklist

- Classify data by freshness needs.
- Decide which layer owns each cache.
- Define invalidation from domain events.

## Practice task

Choose three API calls and write their freshness requirement, cache owner, and invalidation trigger.

## Full note will include

- A cache ownership decision tree.
- Bad-vs-good examples for freshness and invalidation answers.
- A frontend system design checklist for loading, error, empty, and stale states.
- A practice scenario for optimistic updates and rollback.

## Final mental model

Caching is a promise about how wrong the UI is allowed to be, for how long, and what happens when the promise breaks.
